# 11.1 — Boot + Shell (contenedor permanente del Studio)

**Iteración 11.1 de la Fase 11.** Arquitectura funcional del **contenedor permanente** de Pokémon TCG
Studio: el proceso de arranque y el Shell que alojará todas las herramientas futuras. **No** se diseña
ninguna herramienta (ni Galería, ni editores, ni Combat Lab). Ensamblado EXCLUSIVAMENTE con
ComponentStyle existentes. Cadena congelada `Component → ComponentStyle → Visual Tokens → Theme`.
Target Android; densidad `Default` (herramienta densa, con puntero/teclado y toque adecuado).

---

## Finalidad
Ser la **única superficie persistente** del Studio: un marco estable cuyas regiones no se mueven (P9) y
cuyo *contenido* cambia según el Lab activo. El Shell arranca el núcleo (el mismo del juego, Regla de
Oro), restaura la sesión y hospeda los Labs sin conocer sus interioridades.

## Responsabilidades
- Arrancar e inicializar el **núcleo compartido** (engine, animación, render, sesión).
- Mantener el **estado global** (Lab activo, recursos abiertos por Lab, disposición de regiones,
  ajustes) y entregarlo a cada Lab como su porción.
- Ofrecer la **navegación principal** (conmutar de Lab), la **universal** (Command Palette) y la
  **ruta de contexto** (`Lab › Recurso › Variante`).
- Alojar cada Lab en el **host del Workspace** mediante un contrato estable de montaje.
- Gestionar **overlays** transversales (carga, error, operaciones largas) sin desmontar el Shell.

## Layout (regiones permanentes)
```
┌──────────────────────────────────────────────────────────────┐
│ R1 · Barra global (Toolbar): identidad · ruta · acciones · ⌘  │
├─────┬────────────────────────────────────────────────────────┤
│ R2  │ R3 · Host del Workspace (Dock)                          │
│ Rail│   [ el Lab activo monta aquí sus paneles/regiones ]     │
│ de  │   (Biblioteca / Preview / Inspector / Timeline /        │
│ Labs│    Benchmark — vacío en 11.1)                           │
│(Side│                                                         │
│ bar)│                                                         │
├─────┴────────────────────────────────────────────────────────┤
│ R4 · Status Bar: estado del motor · validación · progreso     │
└──────────────────────────────────────────────────────────────┘
   + Overlays transitorios (no son regiones): Command Palette,
     Menús, Tooltips, Diálogos, Toasts, Progress/Busy/Blocking.
```

## Regiones y su composición (todo con ComponentStyle existentes)
- **R0 · Lienzo raíz** — es responsabilidad del **Theme** (`StudioTheme` provee `surfaceCanvas` como
  fondo de ventana), no de un componente. El Shell es una **Plantilla** que solo *coloca organismos*;
  no pinta superficie propia ni lee tokens directamente. Los huecos entre regiones muestran el lienzo
  del Theme.
- **R1 · Barra global** — `ToolbarStyle`. Contiene: identidad (texto `Title`), **ruta de contexto**
  (compuesta: segmentos `ButtonStyle` `Ghost` + separadores con glifo/`DividerStyle`; **no** es un
  componente "Breadcrumb" nuevo), acciones globales (`IconButtonStyle`), disparador del Command Palette
  (`SearchFieldStyle` o `IconButtonStyle`), e indicadores de sesión (`BadgeStyle`).
- **R2 · Rail de Labs** — `SidebarStyle` (contrato `NavItemStyle`): lista persistente de Labs; la
  selección define el Lab activo (barra guía `selectionEdge`). Navegación **primaria**.
- **R3 · Host del Workspace** — `DockStyle` + `PanelStyle` + `TabStyle`. Es el "sitio" estable donde el
  Lab activo monta sus paneles. Los **splitters redimensionables** entre paneles se **componen** de
  `DividerStyle` (línea) + `ResizeHandleStyle` (asa/afordancia), con la interacción regida por el
  Interaction Canon; **no** es un componente "Splitter" nuevo. Recursos abiertos dentro de un Lab =
  `TabStyle` (cerrables). Desplazamiento = `ScrollAreaStyle`/`ScrollbarStyle`.
- **R4 · Status Bar** — `StatusBarStyle`. Segmentos `Status` con tonos `BadgeStyle.Tone`: estado del
  motor, validación, y **segmento de progreso** para operaciones largas.
- **Overlays** — `TooltipStyle`, `MenuStyle`/`ContextMenuStyle`, `PopoverStyle`, `DialogStyle`/
  `ConfirmationDialogStyle`, `SnackbarStyle`/`ToastStyle`, `ProgressOverlayStyle`/`BusyOverlayStyle`/
  `BlockingOverlayStyle`.

## Jerarquía (visual y de foco)
Workspace (contenido, protagonista) › Rail (navegación) › Barra global (contexto/acciones) › Status Bar
(residual, `contentMuted`). El chasis reposa; solo foco/selección/alerta suben (VG-K). Orden de foco =
orden visual: R1 → R2 → R3 → R4.

## Proceso de arranque (Boot)
1. **Arranque en frío:** se inicializa el núcleo compartido. Mientras tanto, `BusyOverlayStyle`
   (spinner) o `SkeletonStyle` en las regiones; sin decisiones del usuario (P11).
2. **Restauración de sesión:** se rehidrata el último estado (Lab activo, recursos abiertos + selección,
   disposición de Dock). 
3. **Éxito:** se monta el Shell con el Lab restaurado.
4. **Primera ejecución / sin sesión:** el Shell se monta con el **Lab por defecto** (Galería de
   Animaciones). Como en 11.1 no existe ese Lab, el host muestra el estado "sin recurso abierto"
   (`EmptyStateStyle`, ver abajo). El Shell queda listo igualmente.
5. **Fallo de núcleo:** `BlockingOverlayStyle` (Plane.Alert) con mensaje + acciones (`ButtonStyle`
   reintentar/salir). No se entra al Shell hasta resolver.

## Pantalla de carga / bienvenida
- **Carga:** no es una pantalla aparte; es el Shell con overlays de carga (`BusyOverlay`/`Skeleton`).
- **Bienvenida (si aplica):** con proyecto único y desarrollador único, **no** hay bienvenida de
  selección. El único "home" posible es el estado vacío del Workspace (`EmptyStateStyle`) cuando no hay
  Lab/recurso activo, con acción primaria "Abrir la Galería de Animaciones".

## Navegación principal y cambio entre módulos
- **Abrir un Lab:** seleccionarlo en el Rail (R2) → el Shell lo monta en R3. **Un solo Lab activo** (P9).
- **Cambiar de Lab:** seleccionar otro ítem del Rail; el estado del Lab anterior se **preserva** en la
  sesión; R3 intercambia contenido (las regiones no se mueven). Cambio iniciado por teclado **no se
  anima** (Motion canon); por puntero, rol `Change`/`Continuity`.
- **Command Palette (universal, teclado):** overlay **compuesto** de material Floating
  (`PopoverStyle`/`DialogStyle`) + `SearchFieldStyle` + `ListViewStyle`/`ListRowStyle` + pistas
  `Shortcut` (vía `MenuStyle`). El Design System ya prevé esta composición (Materials.Floating menciona
  Command Palette). **No** es un componente nuevo.

## Gestión del estado global y restauración de sesión
- **Fuente única de verdad en el Shell:** Lab activo · recursos abiertos + selección por Lab ·
  disposición del Dock · ajustes globales. Cada Lab recibe su porción; no hay estado global duplicado.
- **Persistencia/restauración:** al cerrar se guarda la sesión; al arrancar se rehidrata. La
  restauración es *best-effort*: lo que ya no exista se descarta con aviso (ver recursos inexistentes),
  sin bloquear el arranque.

## Comportamiento cuando no hay ningún módulo abierto
- El Rail siempre tiene un Lab seleccionable, pero si no hay recurso/Lab montado, R3 muestra
  `EmptyStateStyle` (título `Display`, cuerpo `Body` atenuado, acción `ButtonStyle` `Primary`). Es el
  "home" del Studio; nunca una región en blanco sin sentido.

## Comportamiento al cerrar módulos
- Los **Labs no se cierran** (son destinos persistentes del Rail); se **conmutan**.
- Dentro de un Lab, los **recursos** abiertos son `TabStyle` cerrables; al cerrar el último recurso, el
  host vuelve al `EmptyStateStyle` del Lab. El Shell permanece intacto.

## Comportamiento ante recursos inexistentes
- Un recurso restaurado/solicitado que no existe → el host muestra `EmptyStateStyle` en tono de error +
  `ToastStyle`/`SnackbarStyle` (Danger) informando; el recurso se **elimina de la sesión**. El Shell y
  las demás regiones siguen estables (aislamiento del fallo).

## Comportamiento durante operaciones largas
- Determinadas: `ProgressOverlayStyle` acotado a la región afectada + segmento de progreso en la Status
  Bar. Indeterminadas: `BusyOverlayStyle` (spinner). El Shell sigue respondiendo; si la operación es
  cancelable, `Esc` la cancela. Movimiento limitado al progreso (VG-MOV).

## Manejo de errores (tres niveles)
- No bloqueante → `SnackbarStyle`/`ToastStyle`.
- Requiere decisión → `DialogStyle`/`ConfirmationDialogStyle`.
- Crítico / posible pérdida de trabajo → `BlockingOverlayStyle` (Plane.Alert).

## Estados (del Shell como contenedor)
- **rest:** Shell montado con un Lab activo.
- **loading:** overlays de carga durante Boot/operaciones.
- **empty:** `EmptyStateStyle` en el host sin recurso.
- **error:** overlays/estado de error según nivel; recurso inexistente aislado.
- **focus/hover/pressed/selected:** los aportan los organismos (Rail, Tabs, controles); el Shell no
  inventa estados.

## Accesibilidad
- Anillo de foco único (`StudioFocusRing`) en todo elemento interactivo; orden de foco = orden visual.
- Estado nunca solo por color (Rail con barra + `contentEmphasis`; Status con texto además de tono).
- Áreas de toque adecuadas (Android) con la altura de fila de densidad; overlays descartables.
- Contraste reservado; Status Bar residual pero legible.

## Comportamiento con teclado
- Atajo global para abrir el **Command Palette**; `Esc` lo cierra.
- Rail: conmutar de Lab por atajo/`↑↓`+`Enter`.
- `Tab`/`Shift+Tab` recorren; ciclo de regiones (p. ej. `F6`) entre R1→R2→R3→R4.
- Recursos: cerrar la pestaña activa por atajo; `Esc` cancela overlays/operaciones.
- Acciones iniciadas por teclado **no se animan** (Motion canon).

## Reglas de composición
- El Shell es una **Plantilla**: solo *coloca organismos*; su única "superficie" es el lienzo del Theme.
- Cada región consume su ComponentStyle; ninguno lee Visual Tokens directamente.
- Los Labs se montan en el **contrato del host** (R3); el Shell no conoce su interior.
- Un Lab activo; las zonas mantienen su sitio (P9); editar es un modo del Lab, no otra pantalla.
- Elementos compuestos declarados (ruta de contexto, Command Palette, splitter) se construyen **solo**
  con ComponentStyle existentes; ninguno es componente nuevo.

## Restricciones
- Sin abrir proyectos, sin explorador de archivos, sin multi-proyecto (Especialización §2).
- No se diseña ninguna herramienta aquí (solo el contenedor).
- Sin componentes/tokens/principios/estilos/reglas/sistemas nuevos.
